# Meeting library export and recovery

Assumptions: the current SQLite file is the master record; Markdown is portable reading material, while a SQLite backup is the restorable copy. The live installed library and application must remain untouched during development.

1. Add a Settings action to export every meeting to Markdown in a newly named folder chosen with a native folder panel. Flush active notes first, snapshot the SQLite library, then export from that fixed snapshot. Verify a count and report the actual destination; cancellation leaves no folder.
2. Add a separate Settings action to save a standalone, verified SQLite backup. Preserve all master rows and IDs, including provenance, drafts, and summary requests. Exclude the derived calendar cache and rebuild search indexes in the backup.
3. Restore through a retained private validated candidate and a mandatory verified recovery copy of the current library. Process lifetime shared leases exclude current Speakeasy app/MCP/CLI peers, then SQLite's exclusive locking mode stays held from the pre-restore copy through replacement and post-validation. SQLite's backup transaction performs the replacement in place so the original inode and WAL are never swapped. A v6 schema fence makes older builds reject a reopened library. Reject incompatible/corrupt files and fail closed if the current library is unhealthy. A failed rollback or durability check leaves the app paused for manual review, with the recovery path shown; a persistent recovery-required marker blocks new connections until review.
4. Gate restore on idle engine state and flushed editors; pause the calendar worker and library watcher, then refresh the page and resume only authorized calendar syncing. Verify with isolated fixtures, concurrency/failure tests, full Python tests, frontend tests/build, and manual native panel review. Installed-app acceptance is pending because this task does not modify the installed app or the user's real library.

## Verification on 9 October 2026

The full Python suite passed 1,285 tests; the frontend passed 52 tests and its offline production build. Focused tests covered committed WAL writes, more than 500 exported meetings, master-table equality and provenance, incompatible and modified schema, another process holding the library, interrupted SQLite replacement, rollback, and note-save ordering. The final schema-filter regression was included in the full Python run.

A separate, temporary native harness exercised the production Meetings window, WebKit frontend, AppKit panels, bridge, and library code with a synthetic READY engine. Its library, settings, output, and backup paths were pinned under `/private/tmp`; it never started capture, models, Calendar, or the installed app. The native flow passed export cancellation, Markdown export, library backup, restore confirmation cancellation, A-to-B restore, invalid-file refusal, and B-to-retained-recovery-A restore. The meeting list refreshed after each restore. Read-only SQLite checks found the restored and recovery files matched the expected source across every row and column of all 12 master tables, with `integrity_check=ok`, no foreign-key violations, and private `0600` permissions. A recovery file copied alone to a new path validated without sidecars. After a native note edit, the exported Markdown contained the exact edited note, transcript, and summary.

This is native UI acceptance against a synthetic harness, not acceptance of a rebuilt or installed Speakeasy app. Native save-failure behavior, a prolonged editor freeze, live capture, and an actual MCP peer were not exercised in the harness; their relevant backend and frontend boundaries have automated tests. The installed app and real meeting library were not modified or used.
